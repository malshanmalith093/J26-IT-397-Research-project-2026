# Component 2: Personalised Advice (PP1)

This module takes the academic risk output of Component 1 (the ML risk model) and gives each student personalised advice. The advice has four parts: the student's current status, personalised recommendations (each with the main reason behind it), a 3-week improvement guide for the current course, and other helpful tips. The text is generated by an AI model through OpenAI, Azure AI Foundry, Azure OpenAI or any OpenAI-compatible custom endpoint. Rule-based checks find the evidence first, so the model's advice is based on the student's real indicators.

Component 1 is being developed separately, so for PP1 staff send **dummy Component 1 data**. When the real model is ready, it only needs to write the same record format (see `contract.py`).

The course-content chatbot is planned for later and is not part of PP1.

## Who sees what

Everything appears on the existing **Behavioral Profile** page (`/Profiling`) in the sidebar.

| User | What they see on /Profiling |
|---|---|
| Student | **Only their own advice**: latest advice per course, history, and a "new" badge for unread advice. The server takes the user from the login token, so a student cannot load another student's advice. |
| Admin / Moderator | **Send personalised advice**: list of registered students; choose dummy Component 1 data per student (a scenario, a random Low/Medium/High record, or their own values); send to one, several, or all students; bulk import by CSV/JSON using an `email` column; view exactly what each student received and whether they have read it. |

Login works with both the Node and Flask auth backends. They share `JWT_SECRET` and the `research_db.users` collection.

## Setup

```bash
cd python
venv\Scripts\activate            # Windows
pip install -r requirements.txt  # adds the openai package
# macOS: source venv/bin/activate
```

### Choose an AI provider

Add **one** of these to `python/.env`. All options are explained in `.env.example`. The provider is detected automatically; you can also set `LLM_PROVIDER` yourself.

| Provider | Settings in `python/.env` |
|---|---|
| **Azure AI Foundry**: Azure OpenAI models and Foundry models such as DeepSeek, Llama, Mistral, Grok | `AZURE_FOUNDRY_ENDPOINT=https://<resource>.services.ai.azure.com`<br>`AZURE_FOUNDRY_API_KEY=...`<br>`AZURE_FOUNDRY_MODEL=<deployment name>` |
| **OpenAI** | `OPENAI_API_KEY=sk-...`<br>`OPENAI_MODEL=gpt-4.1-mini` |
| **Custom OpenAI-compatible endpoint**: LM Studio, Ollama, vLLM, LiteLLM, OpenRouter, a gateway | `CUSTOM_OPENAI_BASE_URL=http://localhost:11434/v1`<br>`CUSTOM_OPENAI_MODEL=llama3.1`<br>`CUSTOM_OPENAI_API_KEY=` (optional)<br>`CUSTOM_OPENAI_HEADERS={"X-Title":"EduPulse"}` (optional) |
| **Classic Azure OpenAI**: api-version style | `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_API_KEY`, `AZURE_OPENAI_DEPLOYMENT`, `AZURE_OPENAI_API_VERSION` |

**Foundry notes:**

- **Endpoint:** paste the endpoint from the Foundry portal as it is. `…services.ai.azure.com`, `…openai.azure.com`, `…cognitiveservices.azure.com`, a project URL, or a URL ending in `/models` are all converted to the OpenAI v1 route (`…/openai/v1/`). No `api-version` is needed.
- **Model:** `AZURE_FOUNDRY_MODEL` is your **deployment name**, not necessarily the model's own name.
- **Keyless login:** to use your Azure login instead of a key, set `AZURE_FOUNDRY_AUTH=entra`, run `pip install azure-identity`, then run `az login`.

**Models without strict JSON support:** some models and custom endpoints don't support `json_schema` output. The engine automatically tries `json_schema`, then `json_object`, then a plain prompt, and remembers which one worked. It also handles servers that need `max_tokens` instead of `max_completion_tokens`, and replies wrapped in `<think>` blocks or ``` code fences. Set `LLM_JSON_MODE` to force one mode.

**Check the connection.** Run this from the `python` folder:

```bash
python -m Profiling.llm_client
```

It prints the provider, model and endpoint, then makes one small test call. Admins can also click **Test connection** on the Behavioral Profile page. No student data is sent in either test.

Without a provider, or if the AI call fails, the app still works. It sends **offline rule-based advice** and shows the "Offline rule-based" badge. Setting `ADVICE_MODE=fallback` forces this mode (useful if the demo room has no internet).

Run as usual: `python app.py` (port 3000), the Node server (port 8080), and `npm run dev` in `client`.

**Staff account:** registering `admin@sliit.lk` through the Node backend gives the Admin role. You can also set `role: "Admin"` (or `"Moderator"`) on a user in MongoDB.

## PP1 demo script

1. Register 2–3 student accounts and one admin account.
2. Log in as the admin and open **Behavioral Profile**. Each student already has a different dummy scenario selected. Click **Select all → Send to selected**.
3. Click the eye icon on a row to show what that student received. Point out the status, the recommendations, the **"Why this is recommended"** box with its evidence chips, and the improvement guide.
4. Log in as one student and open **Behavioral Profile**. Only that student's advice is shown, with a "new" badge.
5. Back as the admin, change a student's data (for example High risk → Low risk, or enter your own values) and send again. The student sees the new advice, and the old one stays in their history.
6. **Bulk import** tab: download the CSV template (pre-filled for every registered student), edit some values, upload it, then **Validate → Send**.

## How it works

```
Component 1 output (dummy for PP1)
   → contract.normalise_record   validate ranges, accept the flat record or the Appendix 4 payload
   → signals.detect_signals      rule-based concerns/strengths (provisional thresholds)
   → advisor.generate_advice     LLM via llm_client (OpenAI / Foundry / Azure OpenAI / custom), JSON output
   → coerce_advice               fix enum casing, missing lists (for non-strict JSON modes)
   → validate_advice             drop recommendations without a reason; keep only real evidence fields
   → store.save_advice           MongoDB research_db.c2_advice, linked to the user
```

- **Data minimisation:** `previous_gpa` is received but not used. The advice focuses on current behaviour the student can change.
- **Collections:** `c1_risk_outputs` (the Component 1 data sent per user) and `c2_advice` (the advice delivered, with sender and read time; this also acts as the audit log).
- **Requirements covered:** generate personalised recommendations (FR-07) and explain the main reason for each recommendation (FR-08).

## API (`/api/advice`, all require the `x-auth-token` header)

## Tests

```bash
pip install mongomock
python -m unittest Profiling.test_advice -v
```

The 25 tests cover: input validation, the Appendix 4 adapter, the rules, provider detection and Foundry URL handling, the LLM path for each provider (mocked), JSON-mode fallback (json_schema → json_object → prompt), `max_tokens` retry, offline fallback, both token formats, student isolation (student A gets 404 on student B's advice), staff-only endpoints returning 403 for students, and CSV routing by email.
